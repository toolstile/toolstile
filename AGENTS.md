# Toolstile development

Build the independent-user self-hosted MCP gateway. Keep each user’s connections, credentials, devices, agents and activity isolated. Preserve explicit blocks during discovery and execution. Server secrets and database modules must never enter browser exports.

Use TypeScript, React, TanStack Start, oRPC, Better Auth, PostgreSQL and Drizzle. Run the same PostgreSQL schema on a server database or embedded PGlite for local mode. Icons use Phosphor. Use Vite+ (`vp install`, `vp run <script>`, `vp exec <bin>`; pnpm stays the underlying package manager); run local type checks, tests and builds before pushing. CI runs on pushes to main and on pull requests against main, on ephemeral Blacksmith runners (see docs/ci.md). Pull-request runs use the `pull_request` event with read-only permissions and no secrets; never switch them to `pull_request_target` or a self-hosted runner. Check lint, types, production build and fresh/repeated migrations; run the complete disposable PostgreSQL production HTTP suite, including MCP/OAuth protocol coverage, and the PGlite lifecycle and standalone production-output regressions in CI. Keep CI databases disposable. Do not add automated deployment or package publication. Never commit .env files, credentials, generated runtime logs or personal data.

Use TanStack Router paths and validated search params for navigation, tabs, filters, pagination and non-modal record views. Do not store that state only in useState. Keep transient drafts, loading/feedback and secrets in local state. Never put credentials or captured payloads into navigation parameters.

Use StyleX for component styling and shared typed tokens. Preserve the approved light/dark palette, IBM Plex typography, 6px corners and compact spacing. Migrate existing component CSS as it is worked on; global resets/font loading may remain CSS. Compile StyleX in the application build, including reusable UI source.

Read `docs/design.md` before UI changes, including its keyboard-focus, direct row-action, stable inline-editor and non-native-dialog rules.

Use the shared Base UI `SelectField` for dropdown selections. Do not introduce native `select`/`option` controls. Preserve explicit defaults, form serialization, keyboard behavior and associated labels.

Keep all dialogs, their selected records and guided setup presentation out of URL search parameters. Use local UI state for dialogs and persisted server progress for guided setup. Paths, page navigation, filters and non-modal record views continue to use validated URL state. Guided setup must occupy less than half the viewport height, including padding and borders.

Account pages live under `/auth`, and dashboard pages under `/app`. The instance root resolves authentication and redirects; it has no landing page. Show the centered full-page brand/loading screen during authentication resolution, without a sidebar. Preserve established MCP/OAuth endpoints and exact signed authorization query bytes when changing account navigation.

Declare each persisted lifecycle (a status column, nullable timestamps such as `revokedAt`) once, in the module that owns it: the typed state set, its transitions and the predicates other code reads, as `packages/database/src/connection-status.ts` does for connections. Type the Drizzle column with `$type`, write each transition as an update guarded by its allowed prior states, and never overwrite a state another flow owns (sign-in states change only through sign-in). In the UI, a failed refresh after a successful change is not a failed change.

Keep package abstractions grounded in actual consumers in this repository. Extract common code when it replaces real application code here; do not add speculative APIs or unused exports. Reuse existing shared controls and helpers rather than duplicating them in application code.

Use `vp exec vitest related <changed-source-files> --run` for quick checks during editing on leaf files. For shared package changes, prefer the full suite: `vp run test:local [files]` starts its own Node production HTTP fixture with disposable PostgreSQL in Docker and generated keys, then rejects failed, skipped or empty suites. A bare `vp run test` skips those suites and ends with an `INCOMPLETE` skip summary; it is never acceptance. Run `vp run build` first; Docker must be running; no dev server or provider credentials are needed. Keep PGlite persistence, migration, ownership, backup/restore and production-asset tests passing. Add the relevant existing integration tests for HTTP boundaries, migrations/files read from disk and environment-dependent behavior; an empty related selection is not validation. Keep the existing final checks before pushing. Do not repeatedly run the full suite for each small edit.

Parallel agent threads must not share a writable checkout, dev server or database. Give each one its own Git worktree and branch, and remove finished worktrees. The runtime scripts (`scripts/runtime.mjs`, see `docs/development.md`) manage runtime resources only: setup prepares without a server, stop retains storage, resume restores readiness, and teardown before source removal deletes only positively owned runtime resources. There are no lifecycle hooks; run setup and teardown explicitly. Main runtime operations require explicit `--main`. Preserve canonical-path, generation, symlink and unknown-ownership guards. Tests allocate their own production fixture. Before integration, run security checks, lint, types, the Node production build and the complete `test:local` suite. Use one descriptive commit per integrated change, then remove finished worktrees and verify owned processes are stopped.
